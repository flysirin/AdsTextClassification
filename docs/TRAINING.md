# Данные, обучение и перенос

CSV читается в UTF-8 с BOM или без него. Поддерживаются запятая и точка с запятой. Кавычки и переносы внутри поля обрабатываются как часть CSV. Результат в CSV записывается с BOM и разделителем «точка с запятой». Первая строка каждой таблицы содержит заголовки.

```csv
text;label
Продаю деревянный стол;home
Продаю ноутбук и холодильник;electronics|home
Ищу работу поваром;jobs
```

## Разметка и допуск строк

Правила подготовки реализованы 11.11.2026, в рамках первого чекпоинта [Roadmap](ROADMAP.md). Обязательные столбцы — `text` и `label`. Каждая строка должна содержать полный набор подходящих категорий: отсутствие категории считается отрицательной меткой. Гарантированно однокатегорийные данные переразмечать не требуется.

Категории разделяются вертикальной чертой `|`. Пробелы вокруг элементов и повторные категории удаляются, категории сортируются. Например, ` home | electronics | home ` превращается в `electronics|home` и список `["electronics", "home"]`. Текст объявления, включая пробелы, кавычки и переносы, сохраняется. Загрузчик `utils/training_data.py` возвращает подготовленную таблицу с дополнительной колонкой `labels`, содержащей списки, и отчёт. Служебная колонка `_source_record` содержит номер исходной записи с 1 без заголовка и сохраняет связь с исходником после фильтрации; имя зарезервировано загрузчиком. Исходный файл не изменяется; multi-hot кодирование относится к следующему этапу.

Допустимые категории, с учётом регистра:

```text
animals, children, clothing, electronics, food, health, hobby, home,
jobs, no_ads, other, real_estate, services, spam, transport
```

Названия соответствуют справочнику разметки; русские подписи и неизвестные коды автоматически не переименовываются. `other` — самостоятельная содержательная метка объявления вне основных тематик. `review` — служебное состояние неопределённости, оно исключает всю строку, даже в сочетании `review|home`. Пустая разметка не является примером без категорий и тоже исключается. Пустой список результата будущей модели — отдельный случай прогноза, а не метка `review` или `other`.

Для подготовки данных `no_ads` и `spam` используются только отдельно. Их сочетания с другими категориями, включая друг друга, исключаются как конфликт; загрузчик не выбирает победившую категорию и не исправляет смысл разметки. `other` допускается вместе с тематическими категориями. Маршрутизация специальных категорий и новый ответ API будут согласованы отдельно в чекпоинте 6.

Дополнительные поля контроля качества необязательны для обычных таблиц из двух столбцов. Если поле присутствует, оно проверяется для каждой строки:

| Поле | Условие допуска |
| --- | --- |
| `review_required` | Только `false`; допускаются логические значения Excel и строки `true`/`false` без учёта регистра и внешних пробелов. `true`, пустое или неизвестное значение исключают строку. Числа `0`/`1` не заменяют логический флаг |
| `annotation_status` | Только `completed`, без учёта регистра и внешних пробелов. Пустое значение, `pending`, `legacy_unverified` и неизвестные состояния исключают строку |
| `qa_status` | Пустое значение или `done`, без учёта регистра и внешних пробелов. `pending` и любые другие незавершённые/неизвестные состояния исключают строку |

Пустой статус QA допустим: повторная QA-проверка не является обязательным условием для всех строк. Проверки `annotation_status` и `review_required` при этом сохраняются. Наличие только `annotation_status=completed` не отменяет необходимость исключить `review` или незавершённый QA.

## Проверка данных без обучения

Из корня проекта в WSL:

```bash
uv run --locked --extra cpu python -m utils.training_data --input data/train_data/labeled.csv
```

Команда только читает таблицу и выводит JSON-отчёт: `total_rows`, `accepted_rows`, `excluded_rows`, `multilabel_rows` (среди допущенных), `exclusion_reasons` и `examples`. Последнее поле содержит до пяти номеров записей на причину, начиная с 1 без заголовка. Это не физические строки CSV и не `message_id`. Сумма причин может превышать число исключённых записей, поскольку у одной записи бывает несколько нарушений.

| Код причины | Значение |
| --- | --- |
| `empty_text` | Нет непустого текста |
| `empty_label` | Нет разметки |
| `empty_label_element` | Пустая категория: например, `home||electronics` или `home|` |
| `unknown_label` | Категория отсутствует в справочнике |
| `review_label` | Среди меток есть `review` |
| `exclusive_label_conflict` | `no_ads` или `spam` сочетается с другой меткой |
| `review_required` | Флаг дополнительной проверки равен `true` |
| `invalid_review_required` | Флаг присутствует, но пуст или имеет неизвестное значение |
| `annotation_incomplete` | Аннотация не подтверждена как `completed` |
| `qa_incomplete` | QA имеет непустое состояние, отличное от `done` |

Ошибочные строки исключаются из подготовленной таблицы с отражением причин в отчёте. Если нет обязательных столбцов, проверка завершается ошибкой. Если ни одна строка не допущена, команда сначала выводит отчёт, затем завершается с кодом 1. Нулевой код команды означает наличие допущенных строк, но не отсутствие исключений: проверяйте `excluded_rows` и причины.

## Группировка и разделение без утечки повторов

Второй чекпоинт реализует `utils/dataset_split.py`. После допуска строк записи объединяются в связные группы по любому из двух признаков: одинаковый непустой `message_id` или одинаковый нормализованный текст. Связь транзитивна: если две записи имеют общий ID, а третья повторяет текст второй, все три входят в одну группу. Пустые ID не связывают записи между собой; непустые сравниваются по строковому значению без внешних пробелов.

Нормализация `nfkc-casefold-whitespace-v1` выполняет Unicode NFKC, `casefold` и замену последовательностей пробельных символов одним пробелом с удалением внешних пробелов. Пунктуация, ссылки и содержание объявления сохраняются. Нормализованная форма используется только для сравнения, текст обучающего примера не переписывается.

Если внутри группы есть разные наборы меток, исключается вся группа. Списки меток не объединяются автоматически, семантическое решение за разметчика не принимается. В остальных группах оставляется первый пример каждого нормализованного текста; повторные экземпляры исключаются, чтобы не увеличивать их вес. При одном ID и разных текстах сохраняются все различные тексты с одинаковой разметкой, но всегда в одной части.

Разделение выполняется в пропорции **80% обучение / 10% валидация / 10% независимый тест**, по умолчанию с `seed=42`. Группы неделимы, поэтому размеры приблизительные. Сначала распределяются группы редких категорий, затем учитываются недостающая представленность меток и целевые размеры частей. Для каждой оставшейся категории сохраняется хотя бы одна группа в обучении. Категория с единственной группой попадает только в обучение. Алгоритм стремится представить метку во всех частях, но связанные многометочные группы могут препятствовать этому; ограничения явно отражаются в отчёте. Если нельзя получить три непустые части, подготовка завершается понятной ошибкой.

Для сохранения состава частей без обучения выполните из корня проекта в WSL:

```bash
uv run --locked --extra cpu python -m utils.dataset_split \
  --input data/train_data/labeled.csv \
  --output data/prepared/candidate-split \
  --seed 42
```

`--output` должен указывать на **новый каталог**. Существующий каталог или файл не перезаписывается. Создаются два локальных файла:

- `manifest.json`: версия формата, SHA-256 исходного файла, seed, пропорции, нормализация, номера исходных записей в каждой части, состав групп, конфликтующие наборы меток и соответствие удалённых повторов оставленным записям. Тексты объявлений не копируются. Манифест позволяет восстановить состав частей по номерам записей в исходном файле с совпадающим SHA-256.
- `report.json`: отчёт первичного допуска, количество конфликтов и повторов, размеры частей, число положительных примеров и независимых групп каждой категории, попарные пересечения групп, текстов и ID. `missing_categories` перечисляет отсутствующие категории по частям, `low_evaluation_support` — категории с менее чем 10 примерами в валидации или тесте. Порог 10 служит диагностическим сигналом, а не гарантией статистической надёжности.

Если файл изменился во время подготовки, результат не сохраняется. Для воспроизведения нужны тот же исходный файл, seed и версия реализации; состав проверяется по манифесту. Эти локальные JSON исключены действующими правилами Git и Docker; они относятся к подготовке выборки и не меняют контракт трёх файлов модели.

Проверка 11.11.2026 сохранена в `data/prepared/multilabel-2026-11-11/`: из 46 701 допущенной строки исключена 31 строка в 14 конфликтующих группах и 2 015 повторов. Осталось 44 655 примеров: 35 721 / 4 468 / 4 466. Все 15 категорий присутствуют в каждой части; пересечения по всем трём признакам нулевые. Повторное вычисление с тем же seed дало тот же манифест; исходный CSV не изменился.

## Текущее обучение и прогноз

Подготовка многометочной разметки уже поддерживается, но обучение с BCEWithLogitsLoss ещё не реализовано. Сейчас `train.py` выводит отчёт подготовки и допускает обучение только на строках с одной категорией. При наличии допущенной строки с несколькими метками он завершится с объяснением до создания каталога модели, чтобы не обучать составные классы. Исключённые строки с `review` не попадают в обучение и словарь выходов. Полный multilabel-прогноз и переход API запланированы в [Roadmap](ROADMAP.md).

Для текущего однокатегорийного обучения `train.py` использует то же групповое разделение 80/10/10 и выводит его отчёт. Параметр `--seed` управляет разделением и случайностью обучения, по умолчанию 42. CountVectorizer обучается только на обучающей части; валидационные и тестовые тексты не расширяют словарь. Валидация зарезервирована для следующего этапа подбора порогов и пока не используется для изменения модели. Параметр `--epochs` задаёт число эпох, по умолчанию 100. В конце выводятся accuracy и взвешенные precision, recall, F1 на независимых тестовых 10%. При прогнозе сохраняются исходные строки, колонки `predicted_label` и `label` содержат индекс и название одной предсказанной категории.

Для обучения на NVIDIA в WSL запустите Bash-скрипт из корня проекта.

```bash
bash scripts/train_cuda.sh --input data/train_data/ads.xlsx --epochs 100 --model-dir saved/candidate
```

Скрипт использует CUDA-профиль из uv.lock и устройство cuda. При первом запуске uv установит зависимости в .venv-cuda. Если задан UV_PROJECT_ENVIRONMENT, uv использует этот путь. Для интерактивного выбора CSV или XLSX запустите скрипт без --input. Относительные пути считаются от корня проекта. При недоступном GPU train.py завершится с сообщением до чтения таблицы.

Обучайте кандидат в отдельном каталоге. Проверьте его через пакетный прогноз с --model-dir и API с MODEL_PATH. После проверки перенесите все три файла из одного запуска в отдельный каталог релиза на сервере, подключите его к контейнеру и проверьте /health. Для отката верните каталог предыдущего релиза. Загружайте vectorizer.pkl только из доверенного источника. Старый векторизатор из scikit-learn 1.5.1 требует проверки в новом окружении, при несовместимости переобучите комплект из исходной таблицы.

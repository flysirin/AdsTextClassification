# Пороги и оценка multilabel

Дата реализации: **11.11.2026**. Используйте готовый multilabel-кандидат из одного запуска и ту же исходную CSV или XLSX. Переобучение не требуется. Команда работает на CPU и проверяет хеш таблицы, состав частей, порядок категорий и хеши всех трёх файлов кандидата. Модель и таблица остаются неизменными.

## 1. Подобрать пороги на validation

Вместо `saved/candidate` укажите каталог вашего обученного кандидата:

```bash
uv run --locked --extra cpu python evaluate_multilabel.py \
  --model-dir saved/candidate --input data/train_data/labeled.csv \
  --stage tune --objective f1 --output runs/candidate-validation
```

Сначала выбирается общий порог по micro F1, затем порог каждой категории по её F1. Сетка фиксирована: от 0.05 до 0.95 включительно с шагом 0.01. При равном результате выбирается порог ближе к 0.5, затем больший. Ничего на test не подбирается и его оценки не вычисляются.

F1 выбран как начальная цель для баланса precision и recall. Это не численный критерий готовности к эксплуатации. Для частного порога требуется минимум 10 положительных и 10 отрицательных примеров validation (`--min-support`). Иначе используется общий порог и записывается причина. Это начальное правило поддержки, а не гарантия статистической надёжности.

Альтернатива: `--objective precision --min-precision 0.95` максимизирует recall среди порогов с validation precision не ниже указанной. Если общего порога нет, команда останавливается. Если частный порог недостижим или категория редкая, используется общий и причина отражается в `decisions`. Такой резервный порог **не гарантирует** нужную precision каждой категории; даже достижение её на validation не гарантирует её на новых объявлениях.

В новом каталоге появляются локальные аналитические файлы:

- `selection.json`: фиксированные пороги, цель, сетка, причины резервных порогов и происхождение кандидата и данных
- `report.json`: сравнение базового порога 0.5 с выбранными, precision/recall/F1 и support по категориям, micro/macro F1, exact match, отдельно одиночные и смешанные объявления
- `errors.json`: все ошибки с исходным номером записи, текстом и ожидаемыми и выбранными категориями

Правило: sigmoid(logits) **>=** порога. Если ни один выход не прошёл порог, результат — пустой список. Для него принят маршрут на ручную проверку; реализация маршрута в API и Finder остаётся в следующих чекпоинтах.

## 2. Зафиксировать решение и оценить test

Сначала изучите validation-отчёт и согласуйте численные требования к качеству. Затем выполните один итоговый запуск с зафиксированными порогами:

```bash
uv run --locked --extra cpu python evaluate_multilabel.py \
  --model-dir saved/candidate --input data/train_data/labeled.csv \
  --stage test --selection runs/candidate-validation/selection.json \
  --output runs/candidate-test
```

Пороги берутся только из selection, параметры их настройки на этом этапе запрещены. Создаются report и errors для независимого test. Поле `acceptance=not_decided` означает, что программа не объявляет модель готовой к эксплуатации. Не используйте test для дальнейшей настройки порогов. Существующие каталоги отчётов не перезаписываются; технического запрета повторной оценки в новом каталоге нет, дисциплину однократной итоговой проверки соблюдает пользователь.

Отчёты в `runs/` локальны и исключены из Git. Они не являются четвёртым обязательным артефактом модели: рабочий комплект из трёх файлов не меняется. Пороги пока не записываются в модель и не подключаются к Flask, пакетному прогнозу или Telegram Finder. Их контракт и подключение остаются чекпоинтами 5–6.
